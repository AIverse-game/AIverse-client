# 0102：访客穿过传送门的故障特效

状态：已完成。

## 目标与依据

用户（2026-11-11）：再做一个传送门的传送特效，可以是那种 glitch 的感觉。

可观察的变化：脚本访客走过传送门线路时，不再从进口瞬移到出口（或者两门不到 8 个单位时滑过去），而是在两端各出现 0.6 秒的故障效果（两次推送之间穿门、新消息又离画着的位置不到 8 个单位的，仍是走过去）：粉、青、白横条撕开错位、夹着像素噪点，访客在出口抖动、闪没，进口留下一个抖动的残影。

## 范围

- 页面：`render/visitorWalk.ts` 新增 `portalCrossing`（某段时间里穿过的传送门）与 `portalHop`（这一帧是否穿门、从哪到哪）；`render/portalGlitch.ts` 故障效果的时间线；`render/PortalGlitchLayer.ts` 画横条与噪点；`VisitorLayer` 发现穿门、把访客立刻画到出口、抖动与残影；`LobbyLandmark` 导出方块人的身高 `CHARACTER_HEIGHT`；`MapRenderer` 接入。
- 设计文档：修改 [交通：传送](../docs/design/portals.md)。
- 不做：传送门模型本身随穿门闪动；居民的传送（AI 居民已不能传送，见变更 0098）；线路的显示。协议和服务端不变。

## 关键选择

- 穿门由页面从 `visitors` 消息的直线段断点算出，不扩协议。两次推送之间已经穿过门、新消息把访客放到 8 个单位以外的，按穿门处理，从画着的位置跳过去。
- 画面每 1/20 秒跳一次、由访客编号和步数取哈希，是 Claude 的取舍：既有“信号坏了”的跳帧感，又可重现、可测。时长、颜色与条数用户未逐项确认。
- 标签页在后台（帧间隔超过 0.5 秒）时不播，免得回来时一批访客一起闪；两份消息隔了 3 秒以上（连接卡顿、跳过了推送）时，远跳也不当作穿门，免得在没有门的地方闪。
- 故障从访客画着的位置开始（不是线路断点），访客在哪里消失，残影和撕裂就在哪里；残影保持进门时的朝向；访客和残影沿屏幕左右抖动，和横条的错位方向一致。

## 验收条件

- [x] 访客走过线路的断点时，进口和出口都出现故障效果，访客立刻出现在出口（浏览器实测，见下）。
- [x] 只把起点与上段终点不同的段当作传送门，桥头的转弯不算，零长的段跳过；一次走过几个门时取最后一个；到达断点那一刻算穿过（`visitorWalk.test.ts` 的 `portalCrossing`）。
- [x] 一条消息里过断点、新消息远跳都算穿门且从画着的位置出发；近跳和隔太久的消息不算（`visitorWalk.test.ts` 的 `portalHop`）。
- [x] 故障效果的开始、结束、跳帧、可重现、逐渐减弱、横条范围与残影时长（`portalGlitch.test.ts`）。

## 验证证据

- 客户端 `npm run verify`：通过（类型检查、ESLint、33 个文件 335 个测试、构建；在只含本次改动的临时工作树里跑）；`python3 scripts/check_repo.py` 通过。
- 独立审查（子 Agent，只读，两轮）：第一轮没有 P0～P2，确认 6 个 P3（抖动沿身体朝向而非屏幕、残影朝向、隔太久的消息也当穿门、追赶中穿门时进口位置偏、文档与测试不全），均已修复；第二轮确认修复成立，只补了代码地图一处说明。
- 浏览器：另起服务端（端口 8011）和 `npm run dev`（端口 5181），用无头 Chrome（swiftshader）经 CDP 驱动。默认世界没有传送门，所以在页面里包一层 WebSocket，冻结真实的访客推送，再送一份带一个假访客的 `visitors` 消息：从 (64, 84) 走到 (66, 84)，下一段从 (82, 82) 开始；同时把页面的 `performance.now` 放慢到十分之一，以便截图。截图里进口和出口都出现粉青白横条和噪点、访客在出口闪动、进口有残影，约 0.6 秒（慢放后约 6 秒）后画面干净；调试日志确认回调收到的进口、出口坐标正确。这是注入的数据，不是真实对局里访客穿门。
- 未执行：真实对局里访客走线路（需要居民建门并连线）；真实 GPU 上的帧率。
