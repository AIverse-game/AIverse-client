# 0007：操作原语与手动操作

状态：已完成。

## 目标与依据

用户要求：实现操作原语系统；基于当前实现，先提供“移动到某一坐标”这一个原语。原语也要暴露给前端，未接入 AI 时玩家可以手动操作。

可观察的变化：在页面上选中一名居民，填写坐标或直接点击地图地面，居民走到该点；所有打开的页面同时看到新位置。服务端拒绝的操作在面板上显示原因。

## 范围

- 服务端新增 `actions.py`：原语的领域模型与执行（`MoveTo`、`perform`、`ActionRejected`）。以后 AI 驱动居民时调用同一个 `perform`。
- 协议升到 3：客户端 `action` 消息，服务端 `action_result` 回复；世界变化后向所有已握手的连接推送 `state`。所有连接共享同一个世界，`hello` 之前不能操作。
- 客户端：`@aiverse/protocol` 的原语类型；`GameStore.act()` 发送原语、`select()` 记录本地选中的居民；“操作”面板（坐标表单与结果提示）；居民列表可点选；地图上点击居民选中、点击地面移动，选中的居民脚下有圆环。

留给后续：移动速度、每回合距离、障碍物与回合时钟；身份与权限（现在任何连接都能操作任何居民）；AI 接入；其他原语（采集、制作、休息、挂单等）。

## 关键选择

均为可逆的实现选择，移动规则仍是 `docs/status.md` 中的待决定问题：

- **即时到达**：`move_to` 校验居民存在、目标在地图内（闭区间，拒绝 NaN 和无穷），然后直接把居民放到目标点。客户端沿用已有的 400 ms 补间动画表现行走。定下移动规则后在 `actions.py` 内修改，协议不必变。
- **原语与协议分开**：领域层 `actions.py` 不依赖 pydantic 和网络；`protocol.py` 负责把校验过的消息转换成原语。手动操作和以后的 AI 走同一条执行路径。
- **结果分两步返回**：发送者先收到 `action_result`（`ok` 及拒绝时的 `code`、`message`），世界变化再以 `state` 推给每个已握手的连接。格式错误的消息仍回复 `error`/`bad_message`；合法但不被规则允许的操作回复 `action_result` 拒绝，`code` 为 `unknown_resident` 或 `out_of_bounds`。
- **广播顺序**：每个连接有自己的发送队列，处理一帧到入队广播之间没有 `await`，所以不同连接看到的状态先后一致，不会先新后旧。
- **发送队列有界**：`state` 是完整快照，每个连接只保留最新一份待发，排在已有回复之后，所以别人的移动不会让任何连接的队列变长。对该连接自己操作的回复按顺序排队，最多 256 条，超过就退出广播并以 1008 关闭；关闭最多等 5 秒，对端一直不读也会放弃，释放这条连接的状态。
- **选中状态只在本地**：选中哪名居民不发给服务端，存在 `GameStore` 中供面板和地图共用；所选居民从世界中消失时自动取消。
- **协议版本升到 3**：新客户端依赖服务端支持原语，旧版本服务端会直接得到 `protocol_mismatch`，不会在操作时才报 `bad_message`。

## 验证证据

环境：macOS，Chrome 无头模式（swiftshader），经 DevTools 协议驱动。日期 2026-10-26。

- 服务端 `make verify`：ruff、`ruff format --check`、mypy strict 通过；pytest 67 个测试通过（新增原语 9 个、接口 27 个）。
- 客户端 `npm run verify`：两个工作区 tsc、`eslint .`、Vitest 4 个文件 45 个测试、`vite build` 通过。
- 端到端：`uv run aiverse-server --port 8765` 加 Vite 开发服务器（`AIVERSE_SERVER_PORT=8765`），同时打开两个页面 A、B，1400 × 1000：
  - A 在列表中点选阿青，按钮高亮，地图上阿青脚下出现圆环；表单填 (50, 50) 提交，面板显示“已执行”，A、B 的侧栏都变为 (50, 50)。
  - A 点击地图上松木的身体，选中项切换为松木；点击 (80, 30) 处的地面，松木移到 (79.93, 30.01)（像素换算误差），B 同步。
  - 点击画布空白处和页面其他位置，坐标不变，无错误提示；选中居民后在地面上右键、中键点击，不移动。
- 积压上限（真实 uvicorn 进程，临时脚本）：
  - 一个只发不收的客户端连续发 20 万条 `move_to`，服务端在 4 万条以内关闭它，不再为它保留队列。
  - 一个握手后从不读取的原始 TCP 连接，在另一名玩家移动 6000 次期间只保留 1 份待发快照、0 条回复，移动的一方不受影响。
  - 一个连接在一次 TCP 写入中发出 600 条或 5000 条移动（约 62 KB、515 KB），另一个正常读取的页面没有被关闭，只收到合并后的 3～4 条消息。
- 实测中发现：无头模式下后台标签页的 Phaser 循环被暂停，点击不生效、补间停在中途；切到前台后正常。这是测试环境的现象，不是应用缺陷。
- 未执行：服务端拒绝的结果在界面上的显示只有单元测试（表单的 min/max 会先拦住越界输入，正常操作很难触发拒绝）；390 px 手机宽度、触屏点击未实测。

## 交接

已更新 `docs/status.md`、`docs/architecture.md`、`docs/code-map.md` 与服务端 `README.md`。

独立审查首轮：1 个 P2、2 个 P3，均已修复。
- P2：改用发送队列后失去了原先 `await send` 的背压，只发不收或不读取的连接能让服务端内存无限增长。改为有上限的队列，溢出即退出广播并关闭连接，关闭加超时（实测发现 uvicorn 在对端不读时关闭会一直等待）。
- P3：右键、中键点击地面也会移动居民。改为只响应主按键（触屏也算主按键）。
- P3：发出操作后连接断开，或服务端以 `error` 回复，面板一直显示“执行中…”。两种情况都清除该状态。

复核：三处修复成立，但上限同时作用于广播，引入新的 P2。uvicorn 一次读入的多帧会连续处理、不让出事件循环，一个连接突发约 260 条移动，就会让所有正常读取的观察者溢出，被以 1008 关闭。改为状态快照只保留最新一份、回复单独排队计数，并补了测试和实测（见上）。第二次复核未发现问题：观察者在 200 条、600 条突发下都只收到 3 条消息，最终位置正确，没有被关闭。

保留的疑点：
- 一次突发超过 256 条操作的连接，即使在读取，也会因为自己的回复积压而被关闭。手动操作不会触发；以后 AI 批量发送时要考虑这个上限。
- 发送任务遇到意料之外的异常时不会被取回，只在垃圾回收时由 asyncio 记一条日志，不影响其他连接。
- 触屏上按下即提交，可能误触，或在画布上无法滚动页面，未实测。
- 已握手的连接再发一个版本不符的 `hello`，会收到 `protocol_mismatch`，但仍保持已握手；影响很小，暂不改。
- 文档原先写“AI 直接调用 `perform`”，但提交新世界和广播还在 `app.py` 的 WebSocket 处理中。已改写文档措辞，代码留到接入 AI 时再调整。
