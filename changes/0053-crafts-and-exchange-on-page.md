状态：已完成。

## 目标与依据

路线图第 ④ 步“协议与页面显示”（用户 2026-11-04 要求“开始第四步”）。变更 0051、0052 只在服务端和 Agent 工具里实现了晶矿、工坊和交易所，页面上看不到：地图上没有晶矿和工坊，正在挖砂或炼制的居民显示为空闲，也看不到挂单和成交。第 ④ 步拆成三次提交：本次做显示和挖砂、炼制按钮；0054 做结束时的计分折算；0055 做页面下单与撤单。

可观察的变化：

- 地图上画出晶矿（紫色圆圈加晶簇，标编号和剩余储量）和工坊（绿色圆圈加小屋），居民名字后标“挖砂中”“炼制中”。

- “操作”面板显示挖砂、炼制状态；站在晶矿里能挖晶砂，站在工坊里能按配方炼晶核，按钮上写原料和按熟练度估算的用时。
- 新增“交易所”面板：按商品切换，显示最好的 5 个买价和卖价、最近成交价、成交价折线、最近 5 笔成交；选中居民后显示其挂单与到期倒计时，以及哪些成交是该居民的。

## 关键选择

- **成交价折线用状态里的最近成交**：不另记“按商品的成交价历史”。状态带全部商品最近 100 笔成交，页面按商品筛选后画线；某个商品很久没人买卖、又被别的商品挤出这 100 笔时，它的折线会消失。首版交易量不大，等试玩看是否需要单独记历史。
- **成交只发 100 笔、时间取到 0.1 秒**：成交攒满后是状态里最大的部分（审查实测 200 笔、未取整时约 18 KB，是其余部分的 6 倍多），每次世界变化都要发给每个观看者，而面板只显示 5 笔和一条折线。
- **交易所视图带 `viewerId`**：页面换选居民后、服务端回应前，还可能收到按上一名居民生成的状态。页面在 `viewerId` 与当前所选不一致时不显示挂单和“所选居民买入/卖出”，与对话、交易面板的再过滤一致。
- **没有收购点就不显示交易所面板**：交易所在收购点，服务端仍发空的挂单簿。
- **挂单簿发 5 个价位**：Agent 的观察仍是 3 个，页面空间大一些，多看两档。
- **炼制用时由页面估算**：工坊视图带基础用时和熟练度参数，页面按所选居民的已炼数算出“约 N 秒”，只用于显示，实际以服务端为准，与收购价估算一样。
- **晶砂只发拥有量**：和能量一样含报价与卖单里预留的，没有单发携带量。炼制按钮在拥有量不够时置灰，够了但有一部分预留时由服务端拒绝。
- **晶矿与工坊先用程序绘制**：用户提供贴图前用简单图形，和设计文档一致。
- **页面上的炼制花光能量要确认**：和卖能量一样，用掉全部能量会出局，先弹确认。

## 验收条件

- [x] 状态里有晶矿、工坊与配方、居民的晶砂、已炼数、挖砂与炼制状态；交易所的挂单簿只有价位和数量，成交没有双方身份，只给 `view_as` 所选居民标出自己的成交、列出自己的挂单，没选居民时没有挂单；页面换选居民后不把旧状态里的挂单算到新居民名下。
- [x] 页面发出的 `dig_shards`、`refine_crystal` 照常执行并推送；不在晶矿或工坊、原料不够时拒绝原因回到发送者；缺字段回复 `bad_message`。
- [x] 客户端校验拒绝地图外或重复的晶矿、地图外的工坊、在不存在的晶矿挖砂、未知的挂单方向、价格为 0 的成交。
- [x] 挖砂或炼制中的居民在页面上算忙碌，只能说话和退出；站在晶矿或工坊里才能点挖砂、炼制。
- [x] 浏览器里能看到晶矿、工坊、交易所面板和所选居民的挂单。

## 验证证据

- 服务端 `make verify`（审查修复后）：ruff、格式检查、mypy strict 通过，1128 项测试通过（原有 1 条 Starlette 弃用警告）。
- 客户端（审查修复后）：`npm run typecheck`、`npm run lint` 通过，`npx vitest run` 212 项测试通过，`npm run build -w apps/web` 通过。
- 浏览器实测（无头 Chrome 1400 px，经 DevTools 协议点选居民）：脚本世界（种子 7，预先挂了晶砂、能量和 C1 的买卖单，一人挖砂、一人炼 C2）在 8010 端口启动，`vite preview` 代理到它。地图上能看到晶矿 q3（晶簇与储量）和工坊（小屋）；侧栏显示居民的晶砂数和“挖砂中”“炼制中”标签、晶矿与工坊列表和配方；操作面板有挖晶砂和三个炼制按钮，不在范围时置灰并提示；交易所面板显示能量的卖 18 × 20、买 14 × 30，最近成交 18，选中阿青后列出其 3 张挂单和“所选居民卖出”的成交。第一次截图里晶簇太小，已放大一倍再确认。没有实测 390 px 窄屏。
- 当时本机 8000 端口有一局用户正在跑的真实模型对局，测试没有碰它。
- 独立审查（子 Agent，只读）：没有 P0～P2 问题。审查者用真实服务端生成三个视角（不选居民、卖方、买方）、260 笔成交的状态，客户端 `parseServerMessage` 全部通过。确认的 P3 均已修复：
  - 换选居民后，交易所面板短暂把上一名居民的挂单和成交算到新居民名下：加 `viewerId`，不一致时不显示。
  - 200 笔成交让状态约为原来的 7 倍：减到 100 笔，时间取到 0.1 秒。
  - 测试：拆开一个测两件事的服务端测试，补上没选居民时没有挂单、成交时间取整；客户端炼制用时改用服务端测试的同一组数字并注明来源；炼制按钮的原料判断移进 `GameStore.lacksMaterials` 并测试。
  - 文案：晶砂提示改为“可以在交易所和其他居民买卖”；`app.py` 的 `broadcast_world` 注释补上挂单；没有收购点时不显示交易所面板。
- 复核（同一审查者）：修复都成立，没有新问题；用新代码重新生成的三个视角状态客户端都能解析，状态从 18.2～21.3 KB 降到 9.4～11.0 KB。按复核建议补了“带着下一阶晶核能炼 C2”的反例测试。
