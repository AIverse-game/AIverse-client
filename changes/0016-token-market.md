# 0016：token 收购点与市场价

状态：已完成。

## 目标与依据

用户要求（2026-10-28）：实现 token 出售点，让居民用 token 换金币；价格由开发者定，或者制定一个“市场价”机制。

问题：此前金币只有开局的 10000，玩家之间交易只是转手，全场总额固定；token 只能用来走路和采矿，换不成金币，出局又不扣金币。按金币排名时，原地不动是最稳的打法。设计稿第 4 节“钱从哪里来”早已指出需要一个外部买家，原方案是系统收购面包；面包与体力被 token 和矿池取代后，这个来源一直缺位。

本次补上这一环：地图中央有一个收购点，代表镇外的买家，按随卖出量浮动的市场价用金币收购 token。这是除开局资金外金币唯一的新来源。

可观察的变化：地图中央出现收购点；侧栏显示当前收购价，随卖出下跌、随时间回升；居民站在收购点范围内可以卖出 token，金币和排名随之变化。

## 范围

服务端（`aiverse-server`）：

- 新增 `market.py`：收购点 `Market` 的价格规则与 `sell_tokens`，错误类型 `MarketError`。
- `world.py`：`World.market`（可选，默认世界中有一个），校验位置在地图内、压力与时刻有效。
- `layout.py`：收购点放在地图中心；矿池离收购点中心至少 `MARKET_CLEARANCE`，不能在一处既采矿又卖出。
- `actions.py`：新原语 `SellTokens`。卖光携带的 token（且没有其他拥有的 token）照常按耗尽出局。
- `perception.py`：每轮感知附带收购点位置与当前单价，收购价是公开信息，不受感知半径限制。
- `protocol.py`：协议版本 7，世界视图增加 `market`，客户端可发送 `sell_tokens`。

客户端：

- `packages/protocol`：`market` 视图校验、`SellTokensAction`、协议版本 7。
- 按收到状态的本地时刻推算当前单价与卖出若干 token 的估算收入（仅供显示，以服务端为准）。
- 界面：地图上画出收购点；侧栏显示收购价；操作面板在收购点范围内可输入数量卖出，卖光全部 token 前先确认会出局。

留给后续：收购点卖出动作进入活动日志（附近的人看到别人在卖）；多个收购点或收购其他商品；系统卖出 token；价格参数的试玩调参。

## 关键选择

**价格机制：随卖出下跌、随时间回升的市场价。** 不用固定价，也不用设计稿的定额窗口，因为前者没有供需，后者在窗口开头造成抢跑。规则：

- 收购点维护“近期卖出压力” S（token 数）。无人卖出时 S 按半衰期 `MARKET_HALF_LIFE`（60 秒）指数回落。
- 边际单价 `p(S) = MARKET_BASE_PRICE × MARKET_DEPTH / (MARKET_DEPTH + S)`：基准价 20 金币，S 达到 `MARKET_DEPTH`（100）时价格减半。
- 一次卖出 q 个 token，收入是单价从 S 到 S + q 的积分，向下取整：`⌊20 × 100 × ln((100 + S + q) / (100 + S))⌋`，之后 S 增加 q。因此拆成几笔卖与一次卖完收入几乎相同（只差取整），不能靠拆单套利；等价格回升再卖才更划算。
- 举例：平静时卖 30 个得 524 金币（约 17.5/个），一次卖 100 个得 1386（约 13.9/个），卖 300 个得 2772（约 9.2/个）；卖完 100 个后，60 秒后单价从 10 回到约 13.3，3 分钟后约 17.8。

依据：全场 token 约 2400 个（4 × 200 开局加 6 个矿池），走路要消耗一部分。若大部分卖出、均价 10 余金币，整局新增金币约在数万以内，与每人 10000 的底数相比足以拉开排名，又有上限、可以对账。数值未经试玩，都是 `market.py` 中的常量。

其余选择（可逆，未逐项向用户确认）：

- **只有一个收购点，在地图中心，半径 5**。所有人共用一个价格，一人卖出会压低所有人的价格，形成竞争。矿池离它至少 20 单位，卖 token 必须花 token 走过来，产生“燃料与货物”的取舍。
- **只能卖携带的 token**，出售报价中预留的不行；数量须为正整数，不够时以 `not_enough_tokens` 拒绝。
- **收入不足 1 金币时拒绝**（`price_too_low`），不让 token 白白消失；只在压力极高时出现。
- **卖光即出局**：沿用变更 0012 的规则，携带与预留的 token 和进行中的采矿都算拥有，全部为零才出局，金币保留。页面卖光前确认。
- **价格的时间演化在服务端是纯函数**：`Market` 只记录压力和测得压力的游戏时刻，任意时刻的价格由公式算出，不需要计时器，也不额外推送。客户端用同一公式在本地推算显示，与行走动画、倒计时的做法一致。
- **对局结束**：未卖出的 token 不折现，仍只按金币排名。

## 验收条件

- [x] 默认世界中有一个位于地图中心的收购点；任意种子下矿池都离它至少 20 单位。
- [x] 站在收购点范围内（含边缘）的居民卖出 q 个携带的 token，得到按上述公式计算的金币，token 减少 q，压力增加 q；之后的单价随游戏时间按半衰期回升。
- [x] 拆成多笔卖出的总收入不高于一次卖出，差额只来自取整。
- [x] 不在范围内（`not_at_market`）、没有收购点（`not_at_market`）、数量非正整数（`invalid_quantity`）、携带不足（`not_enough_tokens`）、收入不足 1 金币（`price_too_low`）、忙碌、出局、游戏结束时拒绝，世界不变。
- [x] 卖光全部拥有的 token 的居民出局，金币保留；还有预留或采矿中 token 的不出局。
- [x] 感知结果附带收购点位置、半径与当前单价。
- [x] 协议 7：状态中有 `market`；`sell_tokens` 可经 WebSocket 发送，数量不是整数时回复 `bad_message`；客户端拒绝不符合的状态。
- [x] 页面：地图上可见收购点，侧栏显示随时间回升的单价，在范围内可卖出并看到金币、排名与单价变化，两页面同步；卖光前确认。
- [x] 服务端 `make verify`、客户端 `npm run verify` 与 `python3 scripts/check_repo.py` 通过。

独立审查首轮（只读子 Agent，review-change）：1 个 P2、2 个 P3。

- P2：`sell_tokens` 的数量是几百位的整数时，`quote` 在 `take_item` 之前把它转成浮点数而溢出，异常未被接住，该连接断开。已改为先扣 token 再计价（数量不可能超过携带量），补了 `10**400` 的原语测试和 401 位数量的 WebSocket 测试，断言回复 `not_enough_tokens` 且连接仍可用。
- P3：变更登记为已完成而本文仍是实现中、证据留空。本次一并更新。
- P3：页面用含预留的 `tokens` 判断“卖光”和输入上限；有出售报价预留时会多问一次再被服务端拒绝。报价尚未进入协议，页面碰不到，已在代码注释和交接中记下。
- 疑点采纳一项：行走中现价行停止刷新，改为只要能行动且在收购点就每秒刷新。其余疑点（客户端以收到时刻推算的显示误差、同一 seed 的矿池位置与以前不同）属预期，记录在此。`market.pressure_at` 晚于世界时间的校验已有测试（`test_the_world_refuses_an_impossible_market` 末项）。
