# 0044：走路耗 token 减半，结束前公告，提示词补充

状态：已完成。

## 目标与依据

分析最近两局 AI 对局日志后，用户提出：

- 走路消耗太多 token，希望少一点。上一局居民从出发点走到收购点单程就要约 60 token，开局只有 200。
- 游戏结束前 60 秒，由系统向全体居民发事件公告提醒游戏快结束了，措辞只提醒，不鼓励清仓。
- `remember` 的 `term` 经常漏填，导致调用失败（约 18 次一局）。
- 提示词说明“思考的时间也算游戏时间”，并写明笔记 300 字的上限（换了推理更长的模型后，思考一轮动辄 100 秒以上，笔记超长被拒 4 次）。

## 范围

服务端：

- `TOKENS_PER_UNIT` 从 1.0 改为 0.5，走路每单位 0.5 token，向上取整。
- 新增世界里的公告记录 `World.notices`，`lifecycle.announce` 写入；`Game.tick` 在结束前 60 秒（`ENDING_NOTICE_SECONDS`）发一次“The game ends in 60 seconds.”，对局时长不超过 60 秒不发。居民在下一轮感知读到，出现在观察的 `notices`，并唤醒等待中的 Agent（含忙碌中的）。提交 `efe4a4d`。
- `remember` 的 `term` 默认 `short_term`。
- 提示词与工具说明：说明游戏时钟在模型思考时照常走；笔记最多 300 字符，超长会被拒绝；走路耗费（0.5，向上取整）在系统提示词和 `move_to` 工具说明里都随常量显示。
- 脚本 Agent 探索时按真实走路耗费判断够不够 token，不再用曼哈顿距离当耗费。

客户端：协议不变，公告不在协议里，页面暂时看不到；只更新文档。

设计文档：无。

## 关键选择

- 0.5 是我按“少一点”取的减半，用户没有给数字，可再调。
- 公告只在居民下一轮开始时送达。思考很慢的模型（单轮 100～300 秒）在一轮进行中收不到，60 秒提前量对它们偏短；是否提前到 120～180 秒、或在工具返回里附带，留待下一局观察后决定。

## 验收条件

- [x] 走路从 (0,0) 到 (3,4) 耗 3 token，到 (2.5,0) 耗 2。
- [x] 结束前 60 秒向每名居民发一条公告，每人只读到一次；忙碌的 Agent 被唤醒。
- [x] `remember` 不带 `term` 成功并存为短期笔记。
- [x] 系统提示词写明思考耗时算游戏时间、笔记超长被拒；提示词和 `move_to` 工具说明里的走路价格一致。
