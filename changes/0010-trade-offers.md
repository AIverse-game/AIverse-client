# 0010：购买与出售

状态：已完成。

## 目标与依据

用户要求：实现购买和售卖操作，两种行为的先后顺序可以颠倒。A 主动向 B 购买，B 同意后交易完成；也可以 A 主动向 B 售卖，B 同意后交易完成。

可观察的变化：服务端有两个新原语，“发起购买”和“发起出售”。发起方承诺的东西（买方的金币或卖方的物品）立即预留；对方同意后物品和金币互换，拒绝或发起方撤回后预留原样退回。客户端和协议没有变化。

## 范围

- 新增服务端 `trade.py`：两种事件 `PurchaseOffer`（发件人是买方）与 `SaleOffer`（发件人是卖方），基于 [变更 0009](0009-event-queue.md) 的事件框架；金币的物品种类 `COIN`；错误类型 `TradeError`（`invalid_trade`）。
- `actions.py`：新增原语 `OfferToBuy(resident_id, seller_id, kind, quantity, price)` 与 `OfferToSell(resident_id, buyer_id, kind, quantity, price)`。同意、拒绝、撤回沿用已有的 `RespondToEvent`、`WithdrawEvent`。`RejectionCode` 增加 `invalid_trade`。

留给后续：原语与事件进入协议、客户端展示收件箱与物品；初始金币（设计稿为每人 100）；交易的地点或距离限制；事件过期；集市委托与撮合（设计稿第 5 节，与本次的点对点交易是两种机制）；单笔数量和价格的玩法上限（目前只有 10⁹ 的防御性上限）；居民出局时待处理报价的处理（预留不在物品栏中，`clear_items` 清不到）；排行榜把待处理报价中预留的金币计入总额（设计稿要求冻结金币计入）。

## 关键选择

均为可逆的实现选择：

- **金币暂作物品**：金币是物品栏中种类为 `"coin"` 的物品，复用物品栏的存取和“不足时整体拒绝”。设计稿中金币是独立余额，并用于排名；是否拆成单独字段留待接入初始条件和排行榜时决定。不能拿金币交易金币。
- **两种事件，一种规则**：买和卖都是“买方付金币、卖方交物品”，只是发件人不同。两者共用条款与互换逻辑，各自写清预留哪一方：发件人的那一份在发送时扣下，收件人的那一份在同意时才扣。
- **价格是整批的总价**：点对点成交，双方商定的就是一手交钱、一手交货的总数，不涉及单价乘法与取整。
- **价格至少 1 金币、数量至少 1**：设计稿不允许直接赠送；非整数或布尔值、非字符串的种类同样拒绝。条款来自不可信的请求，所以在 `on_send` 中以 `TradeError` 拒绝，而不是 `ValueError`。另设 `MAX_AMOUNT = 10**9` 作为防御性上限（不是平衡数值），错误信息也不回显数值，避免超长整数在转字符串时抛出未捕获的异常。
- **发送时不检查收件人**：收件人在答复前可能挣到金币或做出物品。同意时不足则报告 `not_enough_items`，世界不变，报价仍待处理，可以稍后再同意或拒绝。

## 验收条件

- [x] A 向 B 发起购买：A 的金币立即扣下，B 同意后 A 得到物品、B 得到金币，报价离开队列。
- [x] A 向 B 发起出售：A 的物品立即扣下，B 同意后 B 得到物品、A 得到金币。两个方向条款相同时，成交后的世界完全一样。
- [x] 拒绝或撤回后，双方物品栏恢复到发起前。
- [x] 发起方不足时不能发出；收件人不足时同意失败，报价仍待处理，补足后可以成交。
- [x] 空或非字符串种类、金币本身、数量或价格小于 1 或超过上限、布尔值和浮点数均以 `invalid_trade` 拒绝；已预留的金币或物品不能再次报价；不能与自己交易；未知居民被拒绝。
- [x] 原语经 `perform` 生效，失败转为对应代码的 `ActionRejected`。
- [x] 服务端 `make verify` 通过。
