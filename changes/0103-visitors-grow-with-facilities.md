# 0103：访客随设施增长

状态：已完成（服务端 `make verify` 通过；协议与页面不变）。

## 目标与依据

访客原来固定 200 个，只有每人代表的人次随时间增长。用户（2026-11-11）指出：建得越多，来的人还是那么多，收入就没什么提升；要求人流量随局内总设施增长，可以不是成倍增加。Claude 提出 200 × √(1 + 设施数 ÷ 10)、上限 600，用户要“多一些”，定为 200 × √(1 + 设施数 ÷ 8)。

可观察的变化：镇上同时活动的访客随建成的设施增多，没有设施时 200，8 座约 282，24 座 400，64 座封顶 600；新设施建成后的一两分钟里，多出来的访客陆续从入口进城。

## 范围

服务端（`aiverse-server`）：

- `economy/visitors.py`：`MAX_VISITORS`、`GROWTH_FACILITIES`、`WAIT_FOR_TOWN`、`visitors_drawn`；编号超出的访客留在城外，过一阵再看。
- `game/layout.py`：默认世界的访客池为 600。
- `agents/system_prompt.py`、`agents/observation.py`：系统提示写明公式和例子；观察的 `land.facilities_built`、`land.visitors_drawn`。
- README、测试。

不做：按设施种类或内容加权；页面显示访客数；赞助商预算随访客增长（广告收入仍受赞助商预算限制）。

设计文档：修改 [脚本访客](../docs/design/visitors.md)；另把 [虚拟设施](../docs/design/facilities.md)、[代码地图](../docs/code-map.md)、[项目状态](../docs/status.md) 里“200 个访客”的说法补上增长。

## 关键选择

- **增加访客实体，而不是只加大每人代表的人次**：画面上能看到人变多，拥挤度照常起作用。
- **访客池固定 600，按编号吸引**（Claude）：开局就建好 600 个访客，编号小于当前人数的才进城；其余在城外时间结束时再等 60～120 秒（每次重新掷骰）再看，所以新设施建成后一两分钟内陆续进城，不必每秒检查。设施只增不减，进了城的不会被赶走。
- **所有已建成的设施一样算，场馆只算一座，在建的不算**：用户提问时就是按“全镇已建成的设施，包括广告位、传送门、场馆、花园”说的。
- **上限 600**（Claude，按性能定）：快进模拟里 600 人满员时 CPU 约为 200 人时的 2.2 倍，仍约占一个核的 1.4%。
- **公式只写一处**：`visitors_for(设施数)`，规则和系统提示里的例子都用它。
- **时间权重不变**：每个访客代表的人次仍按 1 + 时间 ÷ 1200 增长，与访客数的增长叠加。

## 验收条件

- [x] 访客数按公式随已建成的设施增长，上限 600；场馆只算一座；在建的不算。
- [x] 编号超出的访客留在城外，60～120 秒后再看；设施够了就进城。
- [x] AI 知道访客随设施增长和此刻的人数。
- [x] 快进模拟里性能可接受。
