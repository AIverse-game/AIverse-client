# 0025：交付合约

状态：已完成。

## 目标与依据

用户要求增加协议机制，规定未来的事件与结果。例如 B 替 A 挖 token，A 付给 B 钱：以后每当 B 交给 A token，A 就付钱。约定可以是单次的，也可以是多次的。用户让开发 Agent 按自己的设计实现。为避免和通信协议混淆，本功能叫“合约”。

## 范围

- 服务端 `economy/contracts.py`：提议事件 `ContractProposal`，生效的合约 `Contract`、`ContractBook`（在 `core/world.py`，世界校验合约双方存在、未出局、游戏未结束），交付、取消、到期、终止与托管金币统计。
- 原语 `ProposeContract`、`Deliver`、`CancelContract`。出局与游戏结束时终止合约，金币总额与排名计入托管，`settle_due`/`next_due` 处理到期。
- Agent：工具 `propose_contract`、`deliver`、`cancel_contract`；观察中的提议、合约与 `coins_in_contracts`；系统提示中的规则说明。
- 不改协议格式和协议版本，客户端代码不变。页面展示留给后续任务，和交易报价一起做。

设计文档：新建 [合约](../docs/design/contracts.md)。

## 关键选择

见设计文档的“争议讨论与决定”：只做“交付即付款”这一种固定条款，签订时托管买方的全部货款，只有供货方能取消，不要求见面，首版不进入协议。

## 验收条件

- [x] 任一方都能发起提议：买方发起时立即预留全部货款，供货方发起时在买方同意时扣款；买方余额不足时同意失败，提议仍待处理；拒绝或撤回时退回预留。
- [x] 每次交付把物品从供货方移给买方，并从托管中向供货方付一批的价款；最后一次交付后合约结束。
- [x] 不是供货方、物品不足、合约不存在或已到期时，交付被拒绝，世界不变；旁人的合约报告为不存在。
- [x] 到期、供货方取消、任一方出局（含交付最后一个 token 后出局）、游戏结束时，余款退回买方。
- [x] 托管的金币计入金币总额和排名。
- [x] 不合理的条款（次数、时长、价格、数量越界，总价超限，非整数）被拒绝。
- [x] Agent 能经工具完成提议、同意、交付和取消，观察中能看到提议和合约。

## 验证证据

- `aiverse-server`：`make verify`（ruff、ruff format --check、mypy strict、pytest）通过，共 579 个测试。其中新增的 `tests/economy/test_contracts.py` 有 29 个，`tests/agents/test_agents.py` 新增 1 个工具与观察测试。
- 本仓库：`python3 scripts/check_repo.py` 通过。客户端代码没有改动，未运行 `npm run verify`。
- 独立审查：没有发现 P0–P2 问题。审查方写了随机模糊测试（3 名居民，3000 个种子，每局 40 步，随机执行提议、答复、交付、取消、出局、报价和时间推进），每一步都检查全体金币总额守恒，结束时检查预留全部退回，结果全部通过。审查提出的 5 条 P3 均已修复：
  - 状态页、架构文档、总体设计中的过时表述；
  - `events.py` 文档字符串的换行；
  - 系统提示和工具说明中补上次数与时长上限。
- 两个待确认疑点也已处理：
  - 设计文档和系统提示写明“行走或采矿中不能交付”；
  - `ContractProposal.check()` 增加 `sender_supplies` 的类型校验，并补了测试。
- 修正了测试辅助函数 `look`：它原来先读世界、后推进时间，导致观察里的游戏时间落后。这个问题只影响测试，运行时的循环已经是先推进时间、再观察。
- 未用真实模型试玩，模型是否会主动签合约尚未观察。
