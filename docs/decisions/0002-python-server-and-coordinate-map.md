# 0002：Python 权威服务端与连续坐标地图

状态：采用。部分替代 [0001](0001-web-stack-and-layering.md)。
日期：2026-10-26。

## 背景

用户要求实现地图模块：由服务端生成一张有限大小的正方形地图，带坐标系统，前端读取后正确渲染。实现前确认了以下决定：

- 现在就写真正的后端，使用 Python。用户不熟悉 Node，需要能自己审阅服务端代码。
- 不要原先的五个区域，也不要网格。居民，以及将来地图上的物品和地点，都有连续的 `x, y` 坐标，可以任意移动。
- 地图采用固定布局。
- 前端彻底切换到 Python 服务端；删除基于五区域的 TypeScript 规则引擎、宿主、规则 Agent 和浏览器内 Worker 演示。
- 本次只做地图与坐标，移动速度和回合节奏留给后续任务。

0001 的前提是规则引擎用 TypeScript 在浏览器和未来 Node 服务端之间共用，现阶段不写后端。这两点已不成立。

## 候选方案

- **服务端语言**：TypeScript/Node 能与前端共用协议类型和规则代码，但用户无法审阅。Python 便于用户审阅；代价是协议要在两种语言中各写一份，靠测试和运行时校验防止不一致。
- **Python Web 框架**：FastAPI（基于 Starlette）原生支持 WebSocket，与 pydantic 结合做输入校验，资料多。只用 `websockets` 库更轻，但以后的 HTTP 接口（房间、配置）要另行搭建。
- **地图模型**：网格地图便于寻路，但用户明确不要。连续坐标更贴近“任意移动”。
- **传输**：WebSocket 支持服务端主动推送，适合以后的回合广播；只读取地图时 HTTP 也够，但很快需要换掉。

## 决定与依据

- 服务端位于与本仓库同级的 `aiverse-server` 目录，使用 Python 3.12+、uv、FastAPI、uvicorn、pydantic；检查工具为 ruff、mypy（strict）、pytest。版本以该目录的 `uv.lock` 为准。
- 客户端经 WebSocket 连接 `/ws`，消息为 JSON 文本帧，键名使用 camelCase。开发与预览时 Vite 把页面的 `/ws` 代理到 `127.0.0.1:8000`；部署时可用 `VITE_SERVER_URL` 指定地址。
- 协议版本升为 2。Python 一侧的定义在 `aiverse_server/protocol.py`，TypeScript 一侧在 `packages/protocol`。客户端用 zod 校验服务端发来的每条消息，包括坐标在地图内、居民 id 不重复，两边不一致时界面报错而不是画出错误画面。
- 坐标系：正方形地图边长为 `size` 个地图单位（当前为 100）。原点 (0, 0) 在左上角（西北角），x 向右（东）增大，y 向下（南）增大，与屏幕方向一致；两轴取值都是闭区间 [0, size] 内的实数。服务端拒绝构造越界或 id 重复的世界。
- 客户端仍只依赖 `@aiverse/protocol`，由 ESLint 检查；渲染层只做“地图单位 × 缩放 + 边距”的换算，不翻转坐标轴。

## 影响

- 采集、制作、休息、回合推进、规则 Agent 演示暂时没有了，需要以后在 Python 服务端重新实现。旧代码保留在 Git 历史里（提交 `11d852a`）。
- 只有静态文件已无法单独演示，GitHub Pages 部署工作流改为只做检查的 CI。
- 协议改动需要同时修改两个项目，并更新两边的测试。尚无自动的跨语言契约测试，目前依靠客户端运行时校验和端到端实测发现不一致。
- 服务端尚无身份认证、Origin 检查和消息大小限制，默认只监听 `127.0.0.1`。对外部署前必须补上。
- 0001 中 React、Vite、npm workspaces、zod 及“客户端只渲染”的原则继续有效；共享 TypeScript 规则引擎、Web Worker 本地服务端和 GitHub Pages 部署的部分被本记录替代。

重新评估条件：需要和客户端共享大量规则代码；Python 服务端的性能或并发不够用；协议漂移频繁出问题，需要从单一来源生成两边的类型。
