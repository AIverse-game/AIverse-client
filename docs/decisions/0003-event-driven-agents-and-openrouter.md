# 0003：事件驱动的 AI 居民与 OpenRouter 模型接入

状态：采用。
日期：2026-10-29。

## 背景

总体设计的核心是“玩家自带的大模型操控居民”，但到变更 0019 为止只有世界规则，没有任何 Agent 驱动居民：感知（`begin_turn`）和记忆（`remember`、`forget`）都没有调用方，交易原语也无人能用，数值无法试玩。

设计稿第 2 节原定 60 个逻辑回合、每回合 20 秒统一结算。之后的变更已经让行走（每秒 2.5 单位）、采矿（10 秒）按真实游戏时间计时，统一回合与现有规则不再吻合。

用户决定（2026-10-29）：调度采用事件驱动；第一家模型服务商用 OpenRouter 上的 NVIDIA 模型。

## 候选方案

- **调度**
  - 固定回合：每 N 秒所有 Agent 同时决策、统一结算，对模型响应速度最公平；但要把行走、采矿改回按回合推进，或在回合内冻结时间，和现有实时规则冲突。
  - 事件驱动：每名居民有自己的循环，空闲或发生与自己有关的事时唤醒 Agent 决策一轮，原语立即执行。直接复用现有时钟和广播；代价是响应快的模型能更早行动。
- **模型接入**
  - 各家官方 SDK：每家写一份，依赖多。
  - OpenRouter：一个 OpenAI 兼容的 HTTP 接口覆盖多家模型，用 `httpx` 直接调用即可，不引入 SDK。

## 决定与依据

- **事件驱动调度**。每个由 Agent 驱动的居民在服务端有一个异步循环：感知（`Game.begin_turn`）→ 交给“大脑”决策一轮，大脑经工具执行原语 → 等待下一次唤醒。唤醒条件：
  - 从忙碌（行走、采矿）变为空闲；
  - 空闲时收到新的报价；
  - 听到别人说的新话（忙碌时也唤醒，因为行走、采矿中可以说话）；
  - 空闲且一段时间内什么也没发生（默认 20 秒），避免选择等待的 Agent 永远睡下去。

  两轮决策的开始至少间隔 3 秒（大脑出错后为 10 秒），限制调用频率，也部分抵消响应速度的优势。数值是可调常量，未经试玩。
- **AI 与网页走同一条执行路径**：`Game.act` 推进时间、执行原语、提交世界并广播，WebSocket 的处理结果也经 `Game.commit` 提交。每次世界变化都会唤醒等待中的 Agent。
- **工具绑定居民**：每个 Agent 拿到的工具只作用于自己的居民，工具参数中没有“行动的居民”。这满足变更 0015 交接中的要求。工具不包括退出游戏：出局没有好处，只会因模型误操作而发生。
- **大脑可替换**：大脑只需实现“看一份观察、调用工具”的一轮决策。先提供一个固定策略的脚本机器人作为基线和测试用对手，再提供 OpenRouter 模型大脑。
- **OpenRouter**：调用 `https://openrouter.ai/api/v1/chat/completions` 的工具调用（function calling）接口；API key 只从环境变量 `OPENROUTER_API_KEY` 读取，不写入仓库或日志。默认模型为 `nvidia/nemotron-3.5-lightning`（支持工具调用、延迟低、价格低），启动时可换成其他 NVIDIA 模型，如 `nvidia/nemotron-3-super-120b-a12b` 或带 `:free` 后缀的免费版本（有速率限制）。
- 每一轮决策是一段独立的对话：系统提示给出规则，用户消息给出本轮观察和上一轮的行动结果，模型可连续调用多次工具，直到不再调用为止。跨轮的连续性靠居民自己写的笔记（变更 0015），不把整局对话历史塞进上下文。

## 影响

- 服务端新增 `agents` 子包与运行时依赖 `httpx`；启动时用 `--agent 居民=大脑` 指定哪些居民由 Agent 驱动，未指定的仍可在页面上手动操作。
- 响应速度影响胜负。若试玩中差异明显，再考虑统一决策窗口或按模型延迟补偿。
- 模型请求在真实时间里进行，一局 20 分钟、每轮至少 3 秒，每名居民最多数百轮；另设每名居民的模型请求上限，防止费用失控。
- 尚无玩家配置界面和“玩家拥有哪名居民”，Agent 由启动参数指定；玩家自带 key、经营方针、房间等留给后续。

重新评估条件：速度差异主导胜负；需要回放或确定性复现；需要接入不兼容 OpenAI 接口的服务商。
