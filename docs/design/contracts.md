相关：[变更 0025](../../changes/0025-delivery-contracts.md)、[变更 0026](../../changes/0026-deals-on-page.md)；服务端 `economy/contracts.py`、`game/actions.py`（`ProposeContract`、`Deliver`、`CancelContract`）、`agents/tools.py`。

## 问题背景

现有的买卖报价（[变更 0010](../../changes/0010-trade-offers.md)）只能一手交钱一手交货，居民之间不能就“以后”的事作出约定。用户希望加一种协议机制，规定未来的事件与结果。例如 B 替 A 挖 token，A 付给 B 金币：以后每当 B 把 token 交给 A，A 就付钱。约定可以是一次性的，也可以是多次的。

在此之前，[总体设计](game-overview.md) 写的是“自然语言不构成合同”“首版不做自动委托合同”。本功能按用户这次的要求改变了这一点：对话仍然不构成合同，但居民可以签订由服务端执行的合约。

“协议”在本项目里已经指客户端与服务端之间的通信协议（有协议版本号），所以本功能在文档和代码中叫“合约”（contract）。

## 设计思路

**合约是什么**：供货方与买方之间的一份条款，规定“供货方每交付一批 `quantity` 个 `kind`，买方付 `price` 金币”，最多 `deliveries` 次，签订后 `duration` 秒到期。`deliveries` 为 1 就是一次性约定。物品可以是任何种类，目前实际有 token 和芯片。

**签订**：复用事件队列。任一方用原语 `ProposeContract` 向对方发出提议（事件种类 `ContractProposal`），对方用 `RespondToEvent` 同意或拒绝，发件人可以用 `WithdrawEvent` 撤回。同意时合约生效，到期时间从这时开始算。

**执行**：

- 签订时，买方的全部货款（`price × deliveries`）从余额中划出，留在合约里（托管）。买方发出提议时就预留，和购买报价一样；供货方发出提议时，在买方同意时扣款，余额不足则同意失败，提议仍待处理。
- 供货方用原语 `Deliver` 交出一批物品，立即从托管中得到这一批的价款。买方不需要再操作，也无法拒付。
- 托管的金币仍计入买方的金币总额和排名，与报价中预留的金币一样。
- 交付和取消与其他原语一样，在行走或采矿中不能进行。供货方定时长时，要留出采矿和走路的时间。

**结束**：最后一批交付后，合约结束。此外以下情况会提前终止合约，余款都退回买方：

- 到期：由服务端时钟的 `settle_due` 处理，`next_due` 包含合约的到期时刻；
- 供货方用 `CancelContract` 取消；
- 任一方出局（含 token 耗尽）；
- 游戏结束。

**Agent**：工具 `propose_contract`（自选 `supplier` 或 `buyer` 角色）、`deliver`、`cancel_contract`；`respond_to_offer` 与 `withdraw_offer` 也用于答复和撤回提议。观察中有 `contract_proposals_to_me`、`my_contract_proposals`、`my_contracts`（含角色、对方、剩余次数、剩余时间、托管金额），以及 `me.coins_in_contracts`。收到提议与收到报价一样会唤醒空闲的居民。系统提示说明了规则，并举了“为别人挖 token 换钱”的例子。

**页面**（变更 0026）：状态中的 `contractProposals` 和 `contracts` 只包含 `view_as` 所选居民参与的提议和合约，和私聊、报价一样。“交易与合约”面板显示生效的合约（所选居民是供货方还是买方、条款、剩余次数、托管金额、按本地时钟倒数的到期时间），以及收到和发出的提议。页面只能看，不能操作。

**数值上限**：每次数量和价格同交易，为 1～10⁹；次数 1～100（`MAX_DELIVERIES`）；时长 1～3600 秒（`MAX_CONTRACT_SECONDS`），但游戏结束会终止所有合约；总货款不超过 10⁹。

## 争议讨论与决定

- **通用规则引擎还是固定条款**：可以让居民写“当某事件发生时执行某结果”的任意规则，也可以只提供固定条款。最终选择固定的“交付即付款”条款（开发 Agent 按用户授权的设计，2026-10-30）。理由：服务端目前能验证的“未来事件”主要是物品交给对方；任意条件既难以校验，模型也难写对。用户举的例子正好是这一种。以后需要其他条件时，新增一种合约种类即可。
- **怎样保证买方付款**：考虑过三种做法：交付时从买方余额自动扣款，扣不到就记违约；只记录违约，不做处罚；签订时托管全部货款。选择托管：合约因此真正有约束力，不需要信用和处罚系统，也与报价的预留机制一致。代价是资金被占用，所以加了到期和余款退回。
- **供货方不交付怎么办**：首版不保证供货方一侧。供货方可以不交付，也可以取消，买方最多拿回余款，损失的只是时间。供货方押金或违约金留待以后。
- **谁能取消**：只有供货方能取消。供货方可能已经为合约投入（买芯片、走到矿池），如果买方能随时取消，托管就失去意义。买方的退出途径是设定较短的时长。双方协商解除留待以后。
- **交付是否要求见面**：不要求，与交易报价一致；交易的地点规则仍待决定，见 [当前状态](../status.md)。
- **是否进入协议和页面**：首版（变更 0025）不进入，托管的金币只体现在金币总额里。之后按用户的要求，和交易报价一起只读显示（变更 0026，协议 12）。可见范围和报价一样只给当事人，理由见 [交易报价](trade-offers.md)。

## 暂未实现的功能

- 页面发起、答复、交付或取消合约（这些原语不在协议中）。
- 供货方押金、违约金、违约记录或信用。
- 买方取消、双方协商解除、修改条款。
- 合约结束或收到交付时不唤醒对方，也没有合约历史：交付和到期后，对方只能从物品、金币和合约列表的变化中看出来。
- 其他条件（例如“采到矿就分成”“先付款后交货”）和三方及以上的合约。
- 上限与时长未经试玩调参；模型是否会主动使用合约，还要用真实模型试玩观察。
