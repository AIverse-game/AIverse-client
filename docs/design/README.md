# 设计文档

每个功能一份设计文档，说明它要解决什么问题、怎样设计、为什么这样定，以及还缺什么。设计文档描述功能的当前设计，随功能演进持续修改。

## 何时新建、何时修改

- **新功能**：新建一份设计文档。新功能指能单独描述的一块能力，例如 AI 居民、程序、对话。
- **调整或补充已有功能**：修改原设计文档，不另建新文档。例如：
  - 改变已有功能的行为或数值；
  - 给它加一个子能力；
  - 实现了“暂未实现的功能”中的一项。

  修改时同步更新设计思路，在“争议讨论与决定”中补上新的取舍，在“暂未实现的功能”中删掉已实现的项或补上新发现的缺口。
- **不改变功能设计的改动**：缺陷修复、重构、文档或流程改动，无需修改设计文档。
- **已有功能还没有设计文档时**：本规则建立前实现的功能（地图、行走、算力泉、收购点、交易、记忆、对话等），下次调整时先为它建一份设计文档，内容从总体设计和相关变更说明中整理，再写入本次修改。

## 写什么

使用 [模板](TEMPLATE.md)，保存为 `short-title.md`。正文简要写四部分：

1. **问题背景**：要解决什么问题，当时的现状和约束。
2. **设计思路**：结构、流程和关键规则。实现细节以代码为准，写出代码位置即可，不逐行复述。
3. **争议讨论与决定**：考虑过的方案、选择及理由，谁在何时决定的。重要技术选择的完整依据写在 [决策记录](../decisions/README.md) 中，这里只写结论并链接。
4. **暂未实现的功能**：已知缺口、有意推迟的部分和已知限制。

## 与其他文档的分工

| 文档 | 回答的问题 | 何时改 |
| --- | --- | --- |
| 设计文档 `docs/design/` | 这个功能现在怎样设计、为什么 | 功能新增或调整时 |
| 变更说明 `changes/` | 这一次任务做了什么、怎样验收、有什么证据 | 任务进行中；完成后不再改 |
| 决策记录 `docs/decisions/` | 一项重要技术选择的依据与影响 | 做出或替代该选择时 |

[总体设计](game-overview.md) 是最初的整体提案，不按单个功能拆分；各功能的设计文档优先于它，冲突时在总体设计中注明并链接。
