# AI 居民

状态：首版已实现，尚未用真实模型试玩。
更新：2026-10-30。
相关：[决策 0003](../decisions/0003-event-driven-agents-and-openrouter.md)、[决策 0004](../decisions/0004-player-configured-llm-endpoints.md)、[变更 0020](../../changes/0020-agent-loop.md)、[变更 0022](../../changes/0022-llm-config-from-page.md)；代码在服务端 `src/aiverse_server/agents/`。

## 问题背景

游戏的核心设定是“玩家的大模型操控居民”，见 [总体设计](game-overview.md) 第 1、6 节。但到变更 0019 为止，服务端只有世界规则：

- 感知（`begin_turn`）和记忆（`remember`、`forget`）没有调用方；
- 报价交易只能由服务端内部调用；
- 没有任何东西在玩这个经济，数值无从验证。

另外，总体设计原定 60 个逻辑回合、每回合 20 秒统一结算。之后行走（每秒 2.5 单位）和采矿（10 秒）都改成了按真实游戏时间计时，统一回合与现有规则不再吻合。

要解决的是：让任意一种“大脑”（固定脚本或大模型）按网页操作同样的规则驱动一名居民，并让玩家用任意一家兼容 OpenAI 接口的模型服务。

## 设计思路

### 整体结构

```text
Game.start_agent / start_llm_agent / stop_agent（启动参数，或页面的 start_agent、stop_agent）
  └─ AgentRunner（每名 Agent 居民一个异步循环，停止时关闭大脑的 HTTP 客户端）
       ├─ Game.begin_turn → observe()：整理成一份观察
       ├─ Brain.take_turn(观察, 工具)：ScriptedBrain 或 ChatCompletionsBrain
       │     └─ ResidentTools：绑定该居民 → Game.act → 执行原语、提交世界并广播
       └─ 睡眠，等待唤醒条件
```

网页的 WebSocket 操作也经 `Game.commit` 提交。所以 AI 和人走同一条执行路径，世界每次变化都会通知等待中的 Agent。

### 一轮决策

1. **感知**：推进时间，感知周围，生成观察。观察包括：
   - 自己的状态：金币、token、芯片、预留量、行走或采矿进度、是否在收购点或矿池；
   - 收购点：现价、芯片价目、距离和走路花费；
   - 已知矿池（按距离排序）、感知范围内的居民；
   - 所有居民的金币和名次；
   - 收到和发出的报价与合约提议、自己参与的合约和最近结束的几份（见 [合约](contracts.md)）、听到的话、附近动态、自己的笔记。
2. **决策**：大脑通过工具行动。工具共 14 个：
   - 行动：`move_to`、`mine`、`sell_tokens`、`buy_chip`、`say`；
   - 交易：`offer_to_buy`、`offer_to_sell`、`respond_to_offer`、`withdraw_offer`（后两个也用于合约提议）；
   - 合约：`propose_contract`、`deliver`、`cancel_contract`；
   - 笔记：`remember`、`forget`。

   参数用严格模式的 pydantic 模型校验，同一份模型也生成给模型看的 JSON Schema。工具返回成功与否、拒绝代码和原因，以及执行后自己的简要状态。参数出错或被拒绝时只返回错误，世界不变。
3. **记录**：每轮的观察、工具调用与结果、大脑的话写成一条记录。控制台打印一行摘要，`--agent-log` 把完整记录写成 JSONL。

### 唤醒规则

| 条件 | 空闲时 | 忙碌时 |
| --- | --- | --- |
| 行走或采矿结束（包括大脑思考期间就结束的） | 唤醒 | — |
| 收到新报价 | 唤醒 | 不唤醒，空闲后处理 |
| 自己的合约不是因自己的行动而结束（对方交完最后一次或取消、到期、对方出局） | 唤醒 | 不唤醒，空闲后处理 |
| 听到别人说的新话 | 唤醒 | 唤醒（行走、采矿中可以说话） |
| 20 秒内什么也没发生 | 唤醒 | 不唤醒 |

两轮开始的间隔至少 3 秒，大脑出错后至少 10 秒。居民出局或游戏结束时循环停止。大脑或记录抛出的异常只记日志，不影响游戏和其他 Agent。

### 两种大脑

- **脚本机器人**（`scripted_brain.py`）：不花钱的基线和测试对手，不说话也不交易。策略：
  - 在收购点时，卖掉多余 token，买得起的最好芯片；
  - 携带 token 多、没有芯片或临近结束时，回收购点（走路花费不够时不出发）；
  - 站在有储量的矿池里就采矿，否则去最近的已知矿池，或去固定探索点找矿池。
- **大模型大脑**（`llm_brain.py`，`ChatCompletionsBrain`）：向 `{API 地址}/chat/completions` 发 OpenAI 兼容的请求，不内置任何厂商。每轮是一段独立的对话。
  - 系统提示给出规则（`system_prompt.py`，数值全部取自代码常量）；
  - 用户消息给出上一轮的行动摘要和本轮观察；
  - 模型可以连续调用工具，直到不再调用；
  - 限制：每轮最多 8 次请求，每局每名居民最多 400 次（停止或更换 Agent 不会重置），每次最多输出 2048 token，超时 60 秒；
  - 跨轮记忆靠居民自己写的笔记。

### 配置与密钥

大模型需要三项设置：API 地址、API key、模型。来源有三处，合并规则是“配置文件覆盖，其余用玩家给的”：

1. **页面**：“AI 驱动”面板。选中居民，填写三项，点“交给 AI”（协议 `start_agent`），就由模型驱动；再点一次会按新配置替换。“停止 AI，改为手动”（`stop_agent`）把居民交回页面。所有页面的居民列表都标出“AI”，面板显示所用模型。页面按居民把填过的设置记在本机 localStorage，没配置过的居民默认填上最近一次用过的。
2. **服务端配置文件**（`server/config.py`）：YAML，`--config` 指定，默认读当前目录的 `aiverse.yml`。`llm.override` 下的 `base_url`、`api_key`、`model` 填了哪项，哪项就对所有由模型驱动的居民生效，代替页面和命令行给的值。`welcome` 只告诉页面哪些项被覆盖（不含具体值），页面把这些输入框置灰，显示“由服务端配置指定”。示例见 `aiverse.example.yml`。
3. **启动参数**：可以重复。

   ```sh
   --agent r1=scripted
   --agent r2=llm[:模型]
   ```

   `llm` 用配置文件中的地址和 key；模型取参数里的，配置文件覆盖了就用配置文件的。缺项时启动报错。没指定的居民仍可在页面上手动操作，也可以从页面交给 AI。

合并后缺项（`missing_llm_setting`）、地址不是 http(s) URL 或 key 不是不含空格的可打印 ASCII（`invalid_llm_setting`，否则 HTTP 客户端会在报错中原样带出 key）、居民不存在、已出局或游戏已结束时，请求被拒绝，用 `agent_result` 说明原因。

key 只放在服务端内存里，用来调用接口：不进状态、控制台、`--agent-log` 或错误信息，设置对象和页面请求的 repr 也隐藏它；HTTP 客户端的异常不串进日志，服务商在错误信息里回显的 key 替换为 `***`。httpx 的请求日志调到 WARNING，因为玩家可能把凭据写进 API 地址。页面上的 key 存在本机浏览器的 localStorage 中。

## 争议讨论与决定

- **调度：固定回合还是事件驱动** → 事件驱动（用户决定，2026-10-29）。
  - 固定回合对模型响应速度最公平，但要把行走、采矿改回按回合推进，与现有实时规则冲突。
  - 事件驱动直接复用现有时钟和广播，代价是响应快的模型能更早行动。3 秒最小间隔可以部分抵消这一点。
  - 速度差异主导胜负时再重新评估。详见决策 0003。
- **模型接入：各家官方 SDK 还是 OpenRouter** → 最初选了 OpenRouter 上的 NVIDIA 模型（用户决定，决策 0003）。
  - 一个 OpenAI 兼容接口覆盖多家模型，用 `httpx` 直接调用，不引入 SDK。
- **只接 OpenRouter，还是任意厂商** → 任意 OpenAI 兼容接口，不内置厂商预设（用户决定，2026-10-29，决策 0004）。
  - 用户指出玩家可能用任何一家的 API；OpenRouter 大脑里只有地址和请求头是它专有的，其余都通用。
  - 曾考虑内置几家常见厂商的地址作为预设，用户否决：玩家自己填地址。
  - 不兼容 OpenAI 接口的厂商以后另写适配器。
- **配置从哪里来** → 页面配置，服务端 YAML 配置文件可以全局覆盖地址、key、模型（用户决定）。
  - 曾考虑按居民分别覆盖，或模型不可覆盖；用户选了全局覆盖、三项都可以覆盖。
  - 页面上的 key 记在 localStorage（用户决定），方便刷新后继续；代价是同一浏览器的其他人能读到。
- **上下文：整局对话历史，还是每轮独立对话** → 每轮独立，加上一轮摘要和居民自己的笔记。
  - 整局历史会让上下文和费用随时间增长。
  - 把记什么交给模型，本身就是游戏的一部分（变更 0015）。
- **工具是否带居民 id、是否提供退出游戏** → 工具绑定居民，参数里没有“谁来做”；不提供退出游戏。
  - 绑定后，模型无法冒充别人。
  - 出局没有好处，只会因模型误操作而发生。
- **观察给多少公开信息** → 位置只给感知范围内的；所有居民的名字、id、金币和名次都给。
  - 这些信息页面上本来就公开，私聊和报价也需要知道对方 id。
- **忙碌时是否唤醒** → 只有听到别人说话时唤醒。
  - 忙碌时唯一能做的有意义的事是说话；报价等空闲后处理即可。
- **大脑思考期间结束的行走或采矿**：独立审查发现，原实现会让 Agent 白等 20 秒。
  - 决定：比较本轮开始前记下的“完成”活动序号，有新完成就唤醒。
- **脚本机器人的验收标准**：原定“终局金币超过开局”。实测多数机器人买 MK3 后亏本，这是经济数值的问题，不是循环的问题。
  - 决定：验收改为“能完成买芯片→采矿→卖出的流程且不出局”。数值另行调整。
- **API key 是否由用户在对话中提供** → 不提供，避免密钥进入对话记录或仓库。最初只从环境变量读取，现在改为页面或配置文件提供，配置文件 `aiverse.yml` 被 Git 忽略。

## 暂未实现的功能

- **真实模型试玩**：还没有向真实的模型服务发过请求，只用模拟的 HTTP 传输和本地的模拟服务测试过。规则提示和工具说明要根据试玩调整。
- **页面 AI 行动日志**：页面看不到 Agent 每轮的想法和动作，需要改协议。
- **玩家归属与鉴权**：页面已能配置模型和 key，但没有“玩家拥有哪名居民”、房间和鉴权，任何页面都能接管任何居民，也能让服务端用配置文件里的 key 发请求；key 在 WebSocket 上明文传输。部署到公网前必须加上鉴权和 TLS。
- **经营方针**：大脑支持 `strategy`，但页面和启动参数都还不能填。
- **从页面启动脚本机器人**：脚本机器人只能由启动参数指定。
- **公平性补偿**：没有统一决策窗口或按模型延迟补偿。
- **模拟与回放**：没有加速的无界面模拟，真实对局要等真实时间；没有回放和确定性复现。
- **其他服务商**：只支持 OpenAI 兼容的 Chat Completions 接口，不兼容的（如只提供原生接口的厂商）还不能用。
- **经济数值**：快进模拟中，6 个矿池在 20 分钟内都被挖空，芯片价格相对矿池总储量偏高，有待和试玩结果一起调整。
